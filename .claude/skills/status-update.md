# /status-update — Draft a status update

You are running `/status-update`. Goal: produce a concise, honest update from
what's actually in the logbook — not a fresh interrogation of the user.

## Steps

### 1. Ask scope (one short message)
- **Audience:** manager, stakeholders, skip-level, the team?
- **Period:** since when? (default: since the last update / this week)
- **Focus:** all tracks, or a specific project?

### 2. Gather from the logbook (brain-first)
Pull from:
- `tasks.md` — what closed, what's in progress, what's blocked.
- `projects/` tracks — decisions and progress in the period.
- `team/` — only if people-relevant to this audience.
Cite nothing the logbook doesn't support. If a claim isn't backed, ask or drop
it.

### 3. Draft
Structure, tuned to audience:
- **Highlights / what moved** — concrete outcomes, impact first.
- **In progress** — what's active and on track.
- **Blockers / risks** — what's stuck and what you need (be specific about the
  ask).
- **Next** — the focus for the coming period.

Keep it tight. A status update is scanned, not read.

### 4. Deliver
Present the draft for the user to edit. Match the audience's channel/tone (a
manager 1:1 note reads differently from a broad stakeholder update). Offer to
adapt length or formality.

## Cross-check
Flag anything that's drifting from `growth/objectives.md`, and note any highlight
that's also a candidate for `growth/evidence.md`.

## Tone
Concise, factual, outcome-first. No filler, no over-claiming.
